## Why

There are two leftovers from S7, both ruled for after the S8 gate:

1. **The e2e database image floats.** `e2e.yml:57` runs the service from `postgres:18`, while the Blueprint pins 18.6 and this machine runs 18.6. You ruled to pin CI to `postgres:18.6` (L147).
2. **`build.yml`'s cache comment is false** (`S7.md` §5.1 item 4). It says a `workflow_run` run "can restore existing caches but cannot create or overwrite them", so "each build starts cold" until a manual run.

## What was checked this session (2026-10-09)

- **The tag exists.** Docker Hub's `postgres:18.6` tag is "active", last updated 2026-10-07 (`hub.docker.com/v2/repositories/library/postgres/tags/18.6`). Today its linux/amd64 digest equals `postgres:18`'s (`sha256:88595310…dc5b`), so the pin changes nothing now; it stops CI drifting to 18.7 unannounced.
- **The log step's filter.** Docker's `ancestor` filter takes `<image-name>[:<tag>]`, and "if you don't specify a tag, the `latest` tag is used" (docs.docker.com/reference/cli/docker/container/ls). So `ancestor=postgres:18` would not match a container made from `postgres:18.6`. The filter must change with the image, or the log step after a red e2e (S7 item 6) finds nothing.
- **The caches.**
  - GitHub's docs, re-read today, still say that runs from `workflow_run` "can restore existing caches but cannot create or overwrite them" in the default branch's scope (docs.github.com, dependency caching, "Cache access for low-trust workflow triggers").
  - But `gh api repos/dev42025pwd/gabay/actions/caches` lists `gradle-Linux-a8b9c772…` and `flutter-android-3.47.5-Linux` under `refs/heads/main`. Both were created 2026-10-08 05:56 UTC by the first build, which was a `workflow_run` run.
  - So on this repository the documented restriction did not apply then. Why is unknown.
  - The comment will state both, and rely on neither.

## What

1. **`e2e.yml`:**
   - `image: postgres:18.6`.
   - The log step's filter becomes `ancestor=postgres:18.6`, and its "no postgres:18 container found" line names 18.6.
   - The header comment says why the image is pinned (the Blueprint pin, L147) and that a patch move is a one-line change with its snapshot.
2. **`build.yml` CACHES comment, rewritten.** It will say:
   - what the docs say (quoted, with the fetch date);
   - what this repository showed (the two caches saved under `refs/heads/main` by run 37734604741, `gh api …/actions/caches`, 2026-10-09);
   - that the job is safe either way, because it runs only after lint passed on a push to `main` of this repository (the `if:` already pinned), so any cache it saves comes from code already on `main`;
   - instead of "each build starts cold": the first run may save the caches, or a manual `workflow_dispatch` run on `main` will.

   No step changes; only comments.
3. **The tests that pin these** (named here, as the rule for changing an existing test requires):
   - `tools/test/workflow-rules.js:366`: the `PostgreSQL 18 service` rule. Its pattern becomes `image: postgres:18.6`. The spec change behind it is L147.
   - `tools/test/workflow-steps.js:107`: the expected text of the log step, with 18.6 in the filter and the message (L147).
   - `tools/test/workflow-snapshots/e2e.yml.snap` and `build.yml.snap`: regenerated by the existing snapshot tool and diffed in the report (L147 for e2e; L145 for build).

   Each one fails against the edited workflow before its update and passes after. `tools/test/verify.test.js:38` only mentions "CI's postgres:18" in a comment; it is reworded to "CI's PostgreSQL service" and is not a test change.
4. **Docs:** the Blueprint's PostgreSQL row drops "until it moves to `postgres:18.6`" and says CI uses `postgres:18.6`. `phase-reports/phase-1/S7.md` §5.1 item 4 gains "Corrected in `<commit>`".
