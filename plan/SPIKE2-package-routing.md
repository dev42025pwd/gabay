# SPIKE2-package-routing — Spike 2: the package format and routing speed, measured

> **Version**: 1.0 | **Date**: 2026-10-09 | **Status**: APPROVED by Genesis Perez, 2026-10-09, with §6's questions ruled (§7), all as recommended; recorded in plan.html with the FF-1 to FF-4 batch (L156: one row per slice) | **Parent**: `plan/PH4-feature-first.md` 1.0 §4, row FF-S2 (L153) | **Decision rows**: D6 and D7 (Spike 2 benchmarks the D6 format), L49 (spikes are throwaway; nothing is ported), L103 (the whole-graph "nearest" sweep), L117 (the latency target set from Spike 2 before P0-06's spec; spike numbers start as provisional settings) | **Approver**: Genesis Perez, product owner

## 1. Why now

P0-03 (FF-3) writes the venue package, and P0-06 (FF-4) routes over it. Five numbers are guesses, each marked UNVERIFIED in `plan.html` or open in the Blueprint:
- the package size (D2 says 0.3–3 MB gzipped, unverified);
- the time to open it on a phone;
- FTS5 search time;
- the time to load the CSR graph blob;
- A* and the whole-graph sweep on a budget phone (Blueprint OQ6, DC12).

Spike 2 measures them before P0-03's format and P0-06's latency target are fixed.

## 2. What it measures

All on one low-end Android phone (open question 1), in release mode, each timing the median and 95th percentile of at least 30 runs after 3 warm-ups. A cold-start figure is reported apart.

| # | Measurement | Feeds |
|---|---|---|
| M1 | Package size, raw and gzipped, for the synthetic venue (§3) | P0-03's format; P0-04's download; D2's 0.3–3 MB claim |
| M2 | Opening the package read-only (`?mode=ro&immutable=1`) with the `sqlite3` FFI package (E-02) | P0-04 |
| M3 | FTS5 search for a few typical queries ("comfort room", a store name, a prefix) | P0-05 |
| M4 | Loading the CSR graph blob into typed arrays inside a long-lived worker isolate | P0-06 |
| M5 | A* between 100 random reachable pairs across floors, metre costs, with the RG2 heuristic | P0-06; **OQ6's latency target** |
| M6 | The whole-graph Dijkstra sweep from one origin (L103 "nearest") | P0-05; DC12's throttle |
| M7 | The same M1–M4 for a FlatBuffers build of the same data (D7's comparison) | D6, confirmed or reopened |
| M8 | Peak memory of the app while M4–M6 run | P0-04, budget phones |

**Not measured, a change from D7's wording:** rendering with `flutter_map`. Since L83 the shopper map is Gabay's own 2.5D renderer, and `flutter_map` is the admin editor's only (E-04, narrowed). Rendering is measured in P0-04 itself, against the real renderer.

## 3. The synthetic venue

- **Size:** 4 floors and about 20,000 graph nodes in total, the size PRD §7 and D7 name (about 100,000 m²).
- **Content:** connectors (escalators one-way, lifts, stairs), walk-through stores, and about 1,500 searchable places with synonyms.
- **How it is made:** generated by a script from parameters, never from a real venue's data. No Demo Malls data, no penthouse data (L48, L123).
- **Package build:** with `better-sqlite3` (E-03) in Node, in the shape Blueprint 3.4–3.5 and D6 describe (FTS5, R*Tree, the CSR blob). It is a first cut of the format, not P0-03's.

## 4. Where it runs, and what is kept

- **Code:** a throwaway folder outside the repository, `C:\Users\User\FlutterProjects\gabay_spike2\`, with its own `git init` so its history is readable (open question 2). Nothing from it is ported into the product (L34, L49). Product code is never copied in either.
- **Its stack:** Flutter and Dart for the phone app, Node 22 for the package builder, `sqlite3` and `better-sqlite3` as in E-02 and E-03, plus a FlatBuffers package for M7 only. The spike is not the product, so its packages need no EXCEPTIONS entry. Their versions are listed in the report.
- **What is kept:**
  - the report, `phase-reports/feature-first/Spike-2.md`, in the repository, with every number, the phone (model, Android version, RAM) and the build commands;
  - the raw timing CSV beside it in the spike folder.
- **No database, no server, no network:** the package file is copied to the phone with `adb push`.
