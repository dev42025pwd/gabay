## 1. How to Use & Conventions

This file answers two questions and no others: **what is the state of X**, and **what is next**. Why a feature exists lives in the PRD; how it is built lives in the Blueprint. If a fact appears in two of the three documents, delete one copy.

- **IDs are permanent.** `P0-01` is allocated once, at filing, and never changes. The prefix records where an entry was *filed*; its current tier is the `Tier` row.
- **Insertion is by letter suffix:** a feature that must sit between `P0-03` and `P0-04` becomes `P0-03A`. Nothing renumbers.
- **Append-only.** Shipped entries move to §6 with their ID intact.
- **No dates, no percentages, no estimates-as-commitments.** Effort is S/M/L; status comes from §2.
- **Who may do what.** Any developer may file an entry. Only the tech lead, meaning Allan Young or Raphael Mendoza, changes a `Tier`, and the change must update `Why this tier`. The product owner does so under Raphael Mendoza's delegation (L115).
- **Sync.** This file is on the companion-file sync table (§8.5) and moves in the same commit as the code it describes.
- **Totals are generated** by `npm run pipeline:totals` once it exists; Phase 1 did not build it (`plan/PH1-rails.md` does not include it). *Until then, the provisional hand count is:* P0 15 · P1 6 · P2 4 (P2-01 cancelled) · P3 4 · archived 0 (recounted 2026-10-07, L121).

### 5.3 Evidence (L121)

Nothing is reported as working without:
- **the verification command's output, pasted** (`npm run verify`, ending `ALL GREEN`, with its exit code), and the output of any other test or query relied on. Never "should work";
- **screenshots for any screen change**, rendered by a test: light and dark, phone and tablet, attached to the PR and the report;
- **the traceability table** (G1) in the PR description.

### 5.4 Test rules

- **A failing test means the code is wrong:** fix the code, not the test (standard §8.4).
- **An existing test changes only when `plan/<id>.md` names it and the spec change behind it** (C1); every changed test is listed with a one-line reason.
- **A flaky test is a failure** (L121): no retry until green, no skip; fix its cause (timing, seed, order) before anything merges.
- **A fixed bug gets a regression test** where one can pin it, and the test file's header names the bug or incident (standard §7.5).
- **No coverage percentage** (L121): coverage is the traceability table; coverage reports may be shown but never gate.
- **Seeds are deterministic**; the suite is re-runnable back to back (§7.1).

### 5.5 Human checks at sign-off (standard §9)

The product owner answers only these: does the change do what `plan/<id>.md` said; is the residual risk acceptable; is the tier still right; does anything belong in Blueprint Part 6 as a named rule.
