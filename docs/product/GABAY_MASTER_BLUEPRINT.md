```xml
<routing_and_auth_constraints>
  URL-shaped CRUD: /api/<resource> with standard verbs; nested one level deep. Lookup reads go
  only through GET /api/lookups/:name (allow-list map; paginated; tenant-scoped; TenantId NULL
  rows = platform defaults).

  Public shopper API: /api/public/* is GET-only, reads PUBLISHED versions only, is cacheable
  (ETag), and is rate-limited with carrier-grade NAT in mind (Public-Read rule). Shopper
  sign-in, deletion, reports (L28) and consented analytics (L42) live OUTSIDE /api/public.

  Middleware order (standard §3.1, verbatim, plus Gabay's additions marked +; asserted by a test):
    [TLS is terminated by Cloud Functions, so the TLS-options step is absent (L98)]
    trust proxy (hop count from env; 1 behind Google's front end)
    -> disable('x-powered-by') -> helmet -> cors (allow-list from CORS_ORIGINS)
    -> body limits (MAX_JSON_BODY, 5 MB; large payloads go through multer)
    -> +requestId -> +actorContext (request-scoped store, filled once auth runs)
    -> audit logger (mounted here; writes on res.on('finish'), so it sees the actor)
    -> /api no-store cache headers -> rate limiters (global on /api; auth limiter on login)
    -> routes [unauthenticated mounts first: /api/public/*, sentinel HMAC ingest;
               then auth (Firebase ID token, firebase-admin verifyIdToken; E-08)
               -> tenantContext -> authorize -> validate(zod) -> handler]
    -> static/uploads -> SPA fallback -> +errorShape
       (E-05: the admin page's SPA fallback is Firebase Hosting's rewrite (L93); Express serves
        no web app, so this step is absent here. Its security headers are set in firebase.json.)
    Startup: the function opens its pg pool on cold start; a request that cannot reach the
    database fails with 503 (there is no listen(): Functions owns the server; L98).

  Roles (L41): SUPERADMIN (IQ, all tenants; tenant override header honoured for superusers
  only, and every act-as is audited), MALL_ADMIN, VENUE_EDITOR (drafts; cannot publish),
  VIEWER. Next release: MERCHANT, UNIT, MAINTENANCE. Access is granted per venue
  (UserVenueGrant). A user may hold roles in several tenants (L121): the tenants are the UserRole
  rows, and each request names one, which tenantContext accepts only if the user has a role there.
  Session (L98, E-08): Firebase Auth ID tokens, verified on every request; refresh, lockout and
  brute-force protection are Firebase Auth's. The accepted ID-token age comes from GlobalSetting.
</routing_and_auth_constraints>
```

## Part 2 — Architectural Blueprint

### 2.1 Tenancy model
- **Tenant** = the mall-operator company. It is hierarchical over everything it owns.
- **Venue** = one mall property: a second scope, flat within a tenant. It contains buildings (main, wings, annexes, parking), levels (indoor, or the outdoor ground), units (nested for facility interiors), openings, objects, amenities, transit points, anchors, connectors and beacons.
- **Platform scope** (no TenantId): roles, permissions, shopper accounts, analytics consent pseudonyms, app versions. Lookups use TenantId NULL for platform defaults.
- **Resolution order per request:** tenant from the principal's tenant binding (or, for SUPERADMIN only, the audited override header) → venue from the request, validated against UserVenueGrant. Any mismatch is a 403.

### 2.2 System diagram and realtime transport
```

     | on device: sqlite3 package (FTS5, R*Tree, CSR graph), BLE channel,            |   (asia-southeast1, maxInstances = 1)   (via SQL Connect, pg)
```

### 2.4 Security layer
The middleware chain from Part 1, in that order, plus three-layer authorization (§3.4):
- **Layer 1, roles:** the closed L41 role set, read from `UserRole` once the Firebase ID token is verified and its UID mapped to `AppUser` (L98, E-08);
- **Layer 2, permission bits:** route × Create/Read/Update/Delete from `RolePermission`, where a `UserPermission` row replaces the role row. The same merge runs at login and in the guard. Publishing is Create on `venue-versions`, which Venue Editors lack;
- **Layer 3, data scope:** the record predicate (TenantId and VenueId), then field redaction.

**Sessions (L98, E-08):** Firebase Auth issues the ID token (about an hour) and handles refresh, lockout and brute-force protection. The API verifies every ID token with `firebase-admin` (`verifyIdToken`, revocation checked), maps the UID to `AppUser` or `ShopperAccount`, and builds the tenant context from the database. **Several tenants (L121, DC28):** the admin page picks a tenant after sign-in (skipped when the user has one) and sends it with every request; `tenantContext` sets `req.tenantCompanyID` only when the user holds a `UserRole` in that tenant, or is SUPERADMIN (whose act-as is audited), and refuses otherwise. The ID-token maximum age the API accepts is a `GlobalSetting`. Retired: `RefreshToken`, `ActiveSessionId`, the lockout columns and DC10. Shopper providers wait on D1b (now: which Firebase providers).

**Separation of duties (L41):** Venue Editors cannot publish.

**Catastrophic-set lints:**
- tenant and venue predicate;
- published-version immutability;
- position privacy (only `lib/core/analytics/` may send position, and only after a consent check);
- Public-Read plus the package allow-list.

**The Foreground manifest lint** blocks background-location permissions.

### 2.5 External integrations layer
- BLE beacons and phone GNSS are device concerns, behind `PositionSource` in `lib/core/positioning/`. The server never sees raw sightings.
- Packages are files: built server-side, downloaded and verified by SHA-256.
- Sentinel ingest (P1+) is machine-to-machine HMAC over raw bytes (§3.17).

## Part 3 — DB Schema Architecture

The executable definition is `db/schema.sql`, **PostgreSQL since L98** (56 tables since 0.11: 0.8 added eleven for L104 and L105, 0.11 removed `WeatherSignal` for L109; re-runnable: a `DO` block that drops every foreign key in the schema, the drop block, then the creates). `db/schema.mssql.sql` is the superseded T-SQL version, kept as history. `DECIMAL(18,4)` stays as written: PostgreSQL treats DECIMAL and NUMERIC as the same type. **DESIGN CHOICE (L81):** `schema.sql` is the single source for columns, types, PK/FK and nullability, and this part does not repeat them. It records what B.2 asks to have annotated: encryption at rest, audit stamping, the temporal policy, exclusions, indexes with the queries they serve, and retention. The alternative, column tables for all 56 tables here, was passed over because a second copy drifts (§8.5). Every index in `schema.sql` carries a `-- serves:` note, and a table without a secondary index says why.

**Temporal policy.** No table is system-versioned. History lives in two places: `AuditLog` (`PayloadDiff` per mutating request) and the immutable `VenueVersion` rows (a correction is a new version). One exception, L104: `StoreStatusChange` keeps every store-status change as its own row, because the status-impact figures need exact change times and `AuditLog`'s capped `PayloadDiff` is not a reliable source. DESIGN CHOICE; the alternative, a history table per venue-model table filled by triggers (PostgreSQL has no built-in system versioning), would win if admins need point-in-time diffs of drafts beyond the audit trail.

**Audit stamping.** Every mutable table carries the four standard audit columns, except these, each for a stated reason:
- `AuditLog`, `RouteTrace`, `AnalyticsEvent`, `SentinelReadingHourly` and `SentinelReadingDaily`: append-only or high-volume (the §3.6 noise filter);
- `AnalyticsDailyVenue`, `AnalyticsDailyUnit`, `AnalyticsDailyCell`, `AnalyticsDailyEdge` and `Forecast`: machine-written by scheduled functions, stamped with `ComputedAt` or `GeneratedAt` (L104, L105);
- `StoreStatusChange`: insert-only, with `CreatedBy` only;
- `AnalyticsConsent`: written by an anonymous device;
- `ShopperAccount`: self-created by the shopper;
- `BeaconPlanItem`, `AppVersion` and `ChangelogEntry`: insert-only, with `CreatedBy` only.

**Encryption at rest.**
- `Sentinel.HmacSecretEnc` is column-encrypted.
- Credentials live in Firebase Auth (L98, E-08): no password hash or refresh token is stored here. `AppUser.FirebaseUid` and `ShopperAccount.FirebaseUid` are identifiers, not secrets.
- PII columns are **not column-encrypted today**: `AppUser.Email` and `DisplayName`; `ShopperAccount.Email`, `ProviderSubject` and `DisplayName`; `AuditLog.IPAddress`. Whether they need it is OQ5.

**Naming.** Tables are singular PascalCase, columns PascalCase, FKs `<Table>Id`. Metres are `DECIMAL(9,3)`, money `DECIMAL(18,4)` (PostgreSQL's NUMERIC), and there are no floats. Timestamps are `TIMESTAMPTZ(3)` with `now()` defaults; identity columns are `GENERATED ALWAYS AS IDENTITY`; JSON is `JSONB` (L98). **Standard audit columns** on every mutable table: `CreatedBy`, `CreatedAt`, `UpdatedBy`, `UpdatedAt`, filled from the actor context (§3.18), with no FK to `AppUser` (this avoids a bootstrap cycle). **Composite tenant FKs:** every venue child references `(TenantId, VenueId)` / `(TenantId, LevelId)`, so a cross-tenant link is refused by the database.

### 3.4 Navigation (L32, L86, L87)
- **`NavConnector`**:
  - type and its metre cost come from the lookup;
  - the from/to endpoints are set for escalators, stairs and ramps;
  - `RiseM` gives the height climbed, which feeds the metre cost;

  - `IsEvacuationOnly` marks connectors used only in an evacuation (L87);

### 3.5 Published versions
**`VenueVersion`**: BUILDING, PUBLISHED or FAILED.
- A CHECK requires a package, a SHA-256 and a timestamp before PUBLISHED.
- **Trigger `TR_VenueVersion_Frozen`** throws on any UPDATE or DELETE of a PUBLISHED row (the Frozen Package rule at the database layer).
- `PackageFormatVersion` is on the §8.5 sync table.
- The index `(TenantId, VenueId, Status, VersionNo DESC)` serves "latest published" and the ETag.

### 3.6 Beacons, sentinels and the planner (invariants 7–9, D9 pending, L40)
- **`Beacon`**:
  - its namespace FK is `(TenantId, ProximityUuid)` → Tenant;
  - `UQ (ProximityUuid, Major, Minor)` serves the publish collision check;
  - `IdentityScheme` is closed (`IBEACON_STATIC`) until D9. D9 input: whichever scheme is chosen reserves an identifier range per level, so a signal through the slab is never trusted (L96);
  - **excluded:** key material and per-shopper sightings.
- **`Sentinel.HmacSecretEnc`** is **encrypted at rest**.
- **`SentinelReadingHourly`** (about 5.3M rows per venue per year; not audit-stamped per row). **Retention:** 90 days, then rolled into **`SentinelReadingDaily`**, kept 25 months. Both carry `VenueId` (invariant 13), with an index `(TenantId, VenueId, time)` that serves the beacon-health trend and the roll-up.
- **`BeaconPlan`** and **`BeaconPlanItem`** hold the planner's three plans (count, cost, P95 GDOP, coverage, inputs JSON) and the placement reason for each item.

### 3.7 Live status (L28, P1)
- **`Closure`** targets either an out-of-service connector or an area. The index `(TenantId, VenueId, EndsAt)` serves the public live-status read.
- There are no shopper reports (L87): the only shopper marking is "Path blocked? Mark it" during an evacuation, which stays on the phone. `ShopperReport`, `ReportCategory` and `ReportStatus` were removed in 0.5, which also retires R3.
- Live status is **derived** from active closures; there is no separate VenueStatus table, so nothing has to be kept in sync.

### 3.8 Shoppers and consented analytics (D1, L42)
- **`ShopperAccount`** is platform-scoped, because one shopper uses many malls. `AuthProvider` holds `password`, `google.com` or `apple.com` (D1b, L109). **Excluded:** position, routes and the parking spot.
- **`AnalyticsConsent`** stores a pseudonym, the consent-text version, and the granted and withdrawn times.
- **`RouteTrace`** stores pseudonymised traces.
  - **No writes until the L42 legal gate clears.**
  - **Retention proposal:** 13 months, for the DPO to confirm.
  - **Since L104** a row is one visit session's displayed dot (at most 1 Hz, while the dot shows), not only the stretch of a route, because visits, time inside and the heat map need the whole visit. The consent text the DPO reviews must say so.
- **`AnalyticsEvent`** (L104): the opted-in shopper's lookups, route starts, reroutes and ends, and arrivals, joined by `SessionId` and `RefId`. Same gate and retention as `RouteTrace`.
- **The nightly roll-up** (L104): `AnalyticsDailyVenue`, `AnalyticsDailyUnit`, `AnalyticsDailyCell` (the heat map) and `AnalyticsDailyEdge` (the busiest walkways), per venue, map version and day. The dashboard reads only these. Each row carries `Shoppers` (distinct pseudonyms), and the API withholds a row built from fewer than `analytics.minGroupN` shoppers. No person-level data reaches the admin.
- **`StoreStatusChange`** (L104): the history of store status, for the status-impact figures. Not shopper data.
- **Forecast inputs and output** (L105): `Holiday` (national rows kept by Gabay staff, local rows by the mall), `MallEvent`, `FootfallCount` (the mall's door counters, from an uploaded CSV) and `Forecast`. Weather was dropped for now (L109), and `WeatherSignal` with it. ## Part 4 — Core Modules & Integration Mapping *(anchors only in Phase 0; each is filled in P1+)*

- **4.1 Publish engine:** validations, then graph generation (L32), then connector costing (L37), then the package (D6), written to Cloud Storage for Firebase and recorded in `StoredFile` with its SHA-256 (L98). It no longer emits "You are here" codes or a print sheet: QR was removed (L107). `publishEngine.service.js`, `graphGenerator.service.js`.
  - **Walls (L92):** publish is refused, with the place shown, if any generated or admin-corrected walkway crosses a wall.
  - **Unreviewed drafts (L108):** publish is refused while any `Unit`, `Opening`, `FloorObject` or `NavConnector` of the venue has `NeedsReview` set (the partial indexes `IX_*_NeedsReview` serve the check); each is listed and shown.
  - **Walk-through stores (L92):** for each store marked `PassThrough`, each door joins a point just inside the store, and those points are joined across its floor. The floor edges cost 1.25× their length (a setting); the steps show the real metres. Every such edge carries the store's unit id.
  - **Passages (L92):** publish finds the places that can't be reached without a walk-through store, and marks those stores as passages for those places in the package.
- **4.2 Routing engine:** A* in a worker isolate over the CSR graph, returning the shortest route in metres (L86). Time to arrive = route cost ÷ 1.2 m/s. One-way escalators only in their direction. Step-free filter: lifts and ramps only, no walkway or door under 1.2 m (L88). The stairs rule (L99, amending L86): a stairs route is the default only when it beats the best no-stairs route by `routing.stairsSaveM` (a `GlobalSetting`, default 144 m of cost), else the no-stairs route leads and the stairs way is the other way; "Prefer stairs" disables the rule; "Avoid stairs" and "Avoid escalators" are strict, with a say-so fallback when nothing else reaches a place. Turn-by-turn directions are derived from the route, landmark first (a bend of 30° or more is a turn; 30–50° only at a fork), and spoken by the voice layer (§4.4).
  - **Heuristic (L79 RG2, in metres):** floor-plan distance plus the cheapest connector metre cost × the number of levels apart. Penalties are always ≥ 1. This is a shared test vector.
  - **Origin (L79 RG3):** snapped to the nearest walkway edge reachable without crossing a wall, using the package's R*Tree.
  - **Shortcuts through stores (L92):** a store-tagged edge is usable only when the store is open (`StoreStatus.IsRoutable`, L83), the shopper's "Shortcuts through stores" setting allows it. It is never used on a step-free route or in an evacuation. A passage is usable on trips to or from the places it serves whatever the setting, step-free and evacuation included. Changing the setting re-routes an active trip. A store crossing is one step, "Walk through *store*".
  - **One other way, unasked (L87):** ban the main route's connectors (or its middle edge if it uses none) and search again. It is shown only if it is longer by more than 0.5 m and shorter than 2× the main route, drawn dotted amber. **Labels (L110):** the other way and each way around are named by what differs from the current route: the connector that differs ("via Elevator B"), the landmark the other passes and the current does not ("past the Bookstore"), or "goes outside".
  - **Find another way (L87), on request:**
    - avoid the walk edges of the next ~30 m, or the first connector ahead as a whole (the 30 m is a setting); if that stretch crosses a store, avoid the whole store, except the one the shopper is inside (L92);
    - offer up to 3 ways around beside "Your current way";
    - each search round doubles the cost of edges already used; a way that overlaps one already listed too much is dropped; ways stay under 2.2× the first way found;
    - "Go this way" switches to the chosen way, and Cancel keeps the current one;
    - venue alerts on the route open this sheet, and nothing is avoided automatically.
  - **Off route (L80):**
    - a deviation is confirmed after 3 updates beyond `routing.offRouteM` (5 m) in corridors, or `routing.offRouteStoreM` (7 m) inside a store (L110, from the design notes), judged on the unsnapped position (L106);
    - falling progress along the route over 3 updates also triggers the wrong-way notice;
    - a refresh keeps the trip's penalty;
    - the route never switches on its own otherwise (L110): no switch when a better route appears; venue alerts only offer the ways around (L87).
  - **Browsing (L110):** while the matched position is inside a store that is not on the route and moves less than `routing.browseMoveM` (a setting), off-route, the wrong-way sound and re-routing are held. After `routing.browseAskS` (default 120 s; DC23) a quiet card asks "Still going to ⟨destination⟩?" (Continue · Pause; no sound or vibration). Leaving the store towards the route resumes guidance with one line; leaving it the other way is an ordinary deviation.
  - The avoidance is per trip and on the device only, never crowd data (L26). The arrival rule is an open item in PRD §6.6; arrival gives the demo's double vibration and confetti.
  - **Evacuation (L87):** the nearest open exit; never lifts; escalators per `Venue.EvacEscalatorsAllowed`; evacuation-only connectors enabled; wheelchair users go to an exit on their level or else the mall's refuge area; a blocked exit or a marked path is avoided on that phone only.

The `PositionSource` exposes a confidence state (live-confident, live-unsure, hand-set, approximate, and since L118 guided) that the guidance reads: hedged wording and the pause, ride and arrival checks only when the position is not live-confident (L99). **L113 amends this:** places and surroundings are always worded suggestively, whatever the state; instructions stay plain; and every ride ends with the floor question whatever the state (DC25). The first live-confident fix replaces a hand-set position (L106).

A place wider than `calibration.maxPlaceM` (default 6 m) does not count (DC18). The offset is a device value, not a position: invariant 4 is unchanged, and nothing is sent. A pick that contradicts strong beacon evidence beyond the plausibility limit is ignored for calibration (DESIGN CHOICE).

    - smoothing 0.5 s while walking, 4 s once still; speed cap 1.8 m/s;
    - freeze: D4b #4 (accelerometer quiet for about 1 s, as ruled; not the spike's 2 s without a step); released by a step, or by 5 updates more than 3 m away;

    - glide: about 500 ms to each new point, at a speed between 0.3 m/s and twice the walking speed, along the matched path on the walkway graph (DC19; the spike's 0.5 m grid search does not exist in the product), with a wall check per frame; a frame-driven render (a 120 ms chase) that ticks only while the dot moves or the cone fades.

If, away from any connector, another floor's beacons dominate for `floor.recoveryWindowS` (default 15 s; DC20), the source reports live-unsure and the app asks "Are you on ⟨level⟩?": yes moves the dot to that floor's nearest walkway; no keeps it and restarts the window. - **4.13 Visit forecasts (L105):** an in-house seasonal model in Node, run nightly after the roll-up (`forecast.service.js`). No new service and no exception. DESIGN CHOICE in each step, alternatives in brackets:
  - **Metrics:** mall visits per day for `forecast.dayHorizonD` (14) days; visits by hour (peak hours) for `forecast.hourHorizonD` (7) days; store visits per ISO week for `forecast.weekHorizonW` (4) weeks; and, where the mall uploads door counts, real footfall per day for 14 days. App figures are of opted-in shoppers; with footfall present the dashboard also shows the app's share of footfall.
  - **Method:** a baseline from the same weekday (and hour) over the last 8 weeks, leaving out days that carry a signal; then one multiplicative effect per signal (each holiday kind, payday (DC16), a mall event day), learned as the median ratio of actual to baseline on that signal's past days. A signal seen fewer than `forecast.minSignalSeen` (2) times is not applied, and the forecast says so. [Holt-Winters or ARIMA in Node; BigQuery ML ARIMA_PLUS, ruled out by L105 for now.]
  - **Range and reliability:** each night the model re-forecasts the last 4 weeks from their own past and measures the error (weighted absolute percentage error, WAPE). The range is the 10th to 90th percentile of those errors around the expected value. A metric is shown only once it has `forecast.minHistoryDays` (56) of history and its WAPE is within `forecast.maxErrorPct` (30, L109), always with the range, the error and "based on shoppers who opted in". Otherwise the card says it is still learning and why.
  - **Inputs:** `Holiday` (national rows by Gabay staff from the yearly proclamations, local rows by the mall), `MallEvent` (entered by the mall admin) and `FootfallCount` (CSV upload, format OQ18). Weather is dropped for now (L109). A store's forecast is withheld under the same `analytics.minGroupN` rule.
  - **Gate:** app-visit forecasts read the roll-up, so they wait for the L42 gate. The footfall forecast uses no shopper data and can run as soon as counts are uploaded.

The UID resolves to an `AppUser` or a `ShopperAccount` (Q12); admin routes accept only an `AppUser` (`requireAdminUser`). Session age is `now − auth_time` (time since sign-in) against the setting `auth.idTokenMaxAgeS` (default 28800 s); a token without `auth_time` is refused. Refusals: 401 for no or bad header, a bad, expired or revoked token, a sign-in older than the limit, or an inactive `AppUser`; 403 for a valid identity with no Gabay account (or a shopper on an admin route); 503 when Firebase or the database cannot be reached. It binds the `AppUser` id as the actor (`runWithActor`); `req.user` carries no tenant (rule 2).

The tenants are the user's `UserRole` rows (L121). Permissions are merged per tenant by `src/auth/permissionMerge.js`: role rows OR-ed (platform roles apply in every tenant), a `UserPermission` row replaces the merged role row for its route, and a route with no row is absent (not granted). `isSuperAdmin` flags SUPERADMIN, which bypasses the rows (Q8); a role is a platform role only on a NULL-tenant `UserRole` row whose `Role.IsPlatformRole` is set, and SUPERADMIN needs both (any other NULL-tenant row is ignored and logged). The permission maps have no prototype. The `PermissionRoute` and default `RolePermission` rows arrive with migration `0001` (P2-S3).
