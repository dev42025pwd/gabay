## 1. What this delivers

On localhost, in the admin page, behind FF-0's development stub and inside FF-SK's admin shell:

- Create, list, search, open and edit a **venue**: the whole property, with its map "up" angle (L111, DC24) and an Active switch (B4). Its boundary (L30, invariant 10) is not typed: the server keeps it as a rectangle covering the venue's largest level until the admin draws it in FF-10 (B2). Venues are never deleted (B4).
- Under a venue, create, list, search, open, edit and delete its **buildings** (main, wing, annex, parking and the tenant's own types), each with a type picked from `BuildingType` through FF-0's `building-types` lookup (rule 5), and an optional map "up" angle (empty means the venue's). A building is deleted only when it has no levels (B4).
- Under a building, create, list, search, open, edit and delete its **indoor levels**. Under a venue, create, edit and delete its one **outdoor ground level** (no building; L30; B7). Each level has an ordinal, real dimensions in metres, an elevation, an optional ceiling height, a grid cell size and an optional "spoken as" name (L112; B6). A level is deleted only when nothing uses it (B4).
- Every form is a `FieldSpec` projection on S9's machinery (rule 7), with a new `ColKind.decimal` (B1). Every list uses `ModuleListScaffold` with search, "Load more", the four states and refresh on return (B3).
- In the client, the write controls are hidden from roles that may not write, from the module registry's read-only marker (B14). The server does not check roles until R2.

## 2. Acceptance criteria

The request's tenant is always `req.tenantCompanyID`, which the stub fills (rule 2; FF-0 §2). Without an `X-Tenant-Id` header that is Demo Malls. In the admin page, FF-SK's development switcher picks the account and, for an account holding two tenants, the tenant, and sends `X-Dev-Act-As` and `X-Tenant-Id` (A10; FF-SK 1.0 §5, ruling 3). FF-1 has no tenant code of its own: the stub still fills `req.tenantCompanyID`. "Refused" means an HTTP 4xx with the standard body `{ error: "<message for a person>" }`, no row written or changed, and never a 500 from a constraint the service could have checked first (standard §3.8). Each criterion that a 2026-10-09 ruling settled names it (for example "B4").

### Venues

- **AC-1:** An admin creates a venue with:
  - Code: required, up to 40 characters;
  - Name: required, up to 200 characters;
  - map "up" angle: 0 to under 360, two decimal places; blank saves the column default, 0;
  - Active: a switch, on by default (B4).

  The form has no boundary field. The server stores the boundary itself (AC-34, B2). The venue is stored under the request's tenant. `CreatedBy` is the acting user (actor context) and `CreatedAt` is set. It appears in the venue list without a manual reload (AC-21). Verify: API test, plus a widget test of the form.
- **AC-2:** An admin opens a venue, changes any of those fields and saves. The changed values are stored, `UpdatedBy` is the acting user and `UpdatedAt` is set. Reopening the venue shows the saved values. Verify: API test, plus a widget test.
- **AC-3:** The venue list shows the tenant's venues only, a page at a time with "Load more", and a search box (350 ms debounce, S9). The search matches Code and Name. The list is sorted by Name (B11). An inactive venue stays listed, marked inactive (B4). It shows all four states: loading, empty (with a way to create the first venue), error (with Retry) and data. Verify: widget test (the four states, search, "Load more", the inactive marker); API test (the search columns, the order, the paging envelope `{ items, totalCount, page, pageSize }`, and a requested `pageSize` above 200 is capped at 200, `MAX_PAGE_SIZE`).
- **AC-4:** A second venue with the same Code in the same tenant is refused with 409 and a message that names the code field. The same Code in another tenant is accepted, because `UQ_Venue_Tenant_Code` is per tenant. Code is stored as typed, trimmed, and uniqueness is exact, as the index is: "aurora" and "AURORA" are two different codes (B11). Verify: API test.

### Buildings

- **AC-5:** From a venue, an admin creates a building with its Name (required, up to 200 characters), its type (required) and, optionally, its map "up" angle (0 to under 360, two decimal places). The type is chosen in S9's async server-search picker (`AsyncLookupPicker`), never a load-all dropdown. The picker gets its rows from FF-0's `lookupFetcher('building-types')`. The building's `VenueId` is the venue it was created from. Verify: API test, plus a widget test.
- **AC-6:** The type picker offers the active platform rows (`TenantId` NULL) and the request tenant's own active rows: for Demo Malls, the platform's MAIN, WING, ANNEX and PARKING, plus whichever of OPEN_AIR, ARENA and STATION the demo seed created for Demo Malls (`db/seeds/lib/demo.js`). It never offers another tenant's rows. If a request names another tenant's `BuildingTypeId` on create or update, it is refused, because services check "same tenant or platform" on every write (DC8, the global-lookup trap). Verify: API test (a Spike Venues request naming a Demo Malls-owned type is refused); widget test (the picker shows only what the fetcher returns).
- **AC-7:** A building whose map "up" angle is left blank stores NULL. The form then states that the venue's angle applies (PRD §6.1, L111, DC24). Clearing an angle that was set stores NULL again. Verify: API test, plus a widget test.
- **AC-8:** The building list for a venue shows each building's Name and its type's label. The label comes from a server-side join on `BuildingType`, never a client-side map from the id (standard §4.10, "lists show the label"). Renaming a type's label changes what the list shows and leaves no building row changed. The search matches Name, and the list is sorted by Name (B11). The list has "Load more" and the four states, as in AC-3. Verify: API test (the label is joined; renaming the type leaves `Building` unchanged; the search column and the order); widget test.
- **AC-9 (definition-of-done item 15 in full, L155; B10):** Building B uses building type T. T is deactivated (`IsActive = FALSE`). The test does this in SQL, because the lookup maintenance screen comes in R11. Then:
  - The admin opens B. The form shows T's label marked "(inactive)" (S9's picker with `currentOption`, fetched through FF-0's `GET /api/lookups/building-types/:id`). It does not show a raw id or an empty field.
  - The admin changes only B's Name and saves. The save succeeds.
  - In the database, B's `BuildingTypeId` is still T.
  - Reopening B shows T's label marked "(inactive)".
  - The picker's list still does not offer T for a new choice.

  Verify (B10): an integration test in `npm run verify` that goes through the real route, service and local database, with the deactivation inside a rolled-back transaction (L151); a widget test (the form holds T and sends the same id back on save); and a manual case in both E2E manuals. No automated browser-level test is built now (that stays with item 9, R12).
- **AC-10 (B10):** A new building cannot be given an inactive type, and an existing building cannot be changed to one:
  - the picker does not offer one (standard §4.10);
  - the server refuses one sent directly with 400 and a message that names the type field, on create, and on an update that changes the building's type to an inactive one;
  - an update that keeps the building's current type unchanged is accepted even when that type is inactive (AC-9).

  Verify: widget test; API test (create with T refused; another building changed to T refused; B keeping T accepted).

### Levels

- **AC-11 (B6):** From a building, an admin creates an indoor level with these fields:
  - Ordinal: required; an integer; 0 is the ground and negative is below (IMDF-style, schema comment).
  - Name: required, up to 100 characters.
  - ShortName: required, up to 10 characters.
  - SpokenName: optional, up to 100 characters (L112; blank stores NULL, so the voice uses Name).
  - ElevationM: three decimal places, any sign; blank saves the column default, 0.
  - WidthM and DepthM: required; three decimal places; above 0.
  - GridCellM: 0.25 to 2.00, two decimal places; blank saves the column default, 1.00.
  - CeilingHeightM: optional, two decimal places; blank stores NULL; above 0 when set (it feeds the L40 mount heights).

  The level is stored with `IsOutdoor = FALSE`, `BuildingId` = that building, and `VenueId` = that building's venue. The ranges the schema does not state (WidthM, DepthM and CeilingHeightM above 0) are checked in the service and the form validators only, with no schema CHECK and no migration (B6). Verify: API test, plus a widget test.
- **AC-12 (B7):** From a venue, an admin creates its outdoor ground level, with `IsOutdoor = TRUE`, `BuildingId` NULL (L30, `CK_Level_OutdoorBuilding`) and `Ordinal` 0, and the other fields of AC-11. A venue has at most one outdoor ground level. A second one is refused with 409 and a message that says the venue already has one. The form shows the ordinal as 0, read-only, and the server sets it; a request naming any other ordinal for an outdoor level is refused with 400. Checked in the service; no migration (B7). Verify: API test, plus a widget test.
- **AC-13:** A level's venue is always its building's venue. A request that pairs a building with a different venue, an outdoor level with a building, or an indoor level without one is refused. It never reaches the database's CHECK or foreign key as a 500. Verify: API test.
- **AC-14:** An admin opens a level, edits any field from AC-11 and saves. The values are stored, with `UpdatedBy` and `UpdatedAt` set. Verify: API test, plus a widget test.
- **AC-15:** The building's level list and the venue's outdoor ground level are ordered by Ordinal, highest first, as a building directory reads top to bottom (B11; the order `IX_Level_Venue` serves, Blueprint §3.3). The building's level list searches Name and ShortName (B11). The list shows Name, ShortName and Ordinal, with "Load more" and the four states. Verify: API test, plus a widget test.

### Forms, validation and errors (all three record kinds)

- **AC-16 (B1):** Each form field is one `FieldSpec` whose `table`, `name`, `kind`, `required`, `maxLength` and `scale` match `db/schema.sql`, and the `schema-forms` linter passes. No view builds a bare `TextField` or `TextFormField` (`no-bare-textfield`). The seven `DECIMAL` columns (`Venue.MapUpDeg`, `Building.MapUpDeg`, `Level.ElevationM`, `WidthM`, `DepthM`, `GridCellM`, `CeilingHeightM`) use a new `ColKind.decimal`, the only kind FF-1 adds to S9's set. It is a numeric input limited to the column's `scale`, with derived scale and range validators; blank means NULL or the column default. `money`, `memo`, `date`, `datetime` and `fkMulti` stay in R11 (B1 widens S9's bound; recorded in the slice row). Verify: `npm run verify` (`schema-forms`, `no-bare-textfield`); `tools/lint/test/schema-forms-real.test.js` covers the new specs; a widget test of the decimal field.
- **AC-17:** The client refuses what the column would refuse, before sending, and names the field in the message (standard §4.6 `Validators`, §4.10). This covers:
  - a missing required value, or one that is whitespace only;
  - text longer than the column's length;
  - an integer that does not parse;
  - more decimal places than the column's scale, or a decimal not in the accepted form (AC-38);
  - a value outside a range: `MapUpDeg` 0 to under 360, `GridCellM` 0.25 to 2.00 (the schema's CHECKs), and `WidthM`, `DepthM` above 0 and `CeilingHeightM` above 0 when set (B6).

  The server refuses the same values with 400 and a message that names the field, so a request that skips the client cannot reach a CHECK as a 500. Verify: widget test (each validator); API test (each case on each record kind).
- **AC-18:** Errors from the API reach the admin through `formatApiError`, and raw exception text is never shown (standard §4.3, §3.8). If a save fails (API unreachable, 4xx or 5xx, including AC-25's 409), the form keeps everything the admin typed, and the admin can retry. Verify: widget test.
- **AC-19:** The read-only columns are never form inputs (standard §4.10): `VenueId`, `BuildingId`, `LevelId`, `TenantId`, `IsOutdoor` (set by where the level was created from), `Venue.BoundaryGeoJson` (AC-34), and the four audit stamps. Verify: widget test, plus review of the specs.
- **AC-20:** Tapping Save twice in a row creates one record, because Save is disabled while a save is in flight. Verify: widget test.
- **AC-21 (B3):** After a create, an edit or a delete, the list the admin returns to shows the change without a manual reload (definition-of-done item 7, `didPopNext`). Refresh on return is added to the shared list machinery (`ModuleListScaffold` / `PagedListNotifier`) in FF-1, not built per screen. Verify: widget test of the shared machinery, plus each of the three lists.

### Remove, deactivate and concurrent edits

- **AC-24 (B4):** Removing records:
  - **Venue:** an Active switch (`IsActive`, a `flag` `FieldSpec`) and no delete; no delete route exists for a venue. An inactive venue stays listed, marked inactive, and still opens for editing and for adding buildings and levels. What publish and the shopper side do with an inactive venue belongs to FF-3 and FF-4.
  - **Building:** deleted only when it has no levels. Otherwise refused with 409 and a message that says it still has levels.
  - **Level:** deleted only when no other row references it. Otherwise refused with 409 and a message that names what uses it (for example units or beacons), never the database's text (standard §4.10).
  - The delete action is shown only on an existing building or level. Its confirmation's default and focused action is Cancel (standard §4.6). After a delete, the admin returns to the list, which no longer shows the record (AC-21).

  Verify: API test (each delete allowed and refused; no venue delete route); widget test (the confirmation defaults to Cancel; the Active switch).
- **AC-25 (B5):** Optimistic concurrency on every venue, building and level edit. The form sends the `UpdatedAt` it loaded (empty for a record never edited). If the row's `UpdatedAt` has changed since, the save is refused with 409 and a message such as "Someone else changed this venue. Reload to see their change" (standard §3.9), nothing is written, and the form keeps the admin's values (AC-18). An edit with the current `UpdatedAt` succeeds. No schema change. Verify: API test (a stale token refused on each kind; a never-edited row's empty token accepted once, then stale); widget test (the 409 shown, values kept).

### Added in r2 (rulings of 2026-10-09)

- **AC-34 (B2, the derived boundary):** The venue's `BoundaryGeoJson` is set by the server, never by the client:
  - on venue create, a zero-size rectangle at (0,0);
  - after every level create, edit and delete under the venue (the outdoor ground level included), a closed GeoJSON polygon rectangle from (0,0) to (the largest `WidthM`, the largest `DepthM`) among the venue's levels (plan DC-9);
  - when the venue's last level is deleted, the zero-size rectangle again.

  Updating the boundary does not change the venue's `UpdatedAt`, so an open venue form is not made stale by a level change (plan DC-9; AC-25). A boundary sent in a request body is ignored, never written. The venue form shows a note that the site outline covers the largest level until it is drawn in the map editor (FF-10). FF-3's publish refuses a zero-size boundary (FF-3's spec owns that check). Verify: API test (zero on create; after a create, an edit and a delete of levels; back to zero after the last delete; the venue's `UpdatedAt` unchanged; a body `boundary` ignored).
- **AC-35 (B7, distinct ordinals):** The levels of one building have distinct ordinals. A create, or an edit that changes the ordinal, to one another level of the same building already has is refused with 409 and a message that names the ordinal. The same ordinal in two different buildings of one venue is accepted. Saving a level with its own unchanged ordinal is accepted. Checked in the service; no migration. Verify: API test.
- **AC-36 (B14, client-side hiding of writes before R2):** On FF-1's screens, the write controls follow FF-SK's module registry and its read-only marker for the role the switcher has chosen:
  - VIEWER: no New, Save or Delete on any FF-1 screen, and every form opens read-only (the Active switch included).
  - VENUE_EDITOR: no New on the venue list; the venue form is read-only with no Save; buildings and levels (the outdoor ground level included) keep New, Save and Delete, as AC-31 gives them.
  - SUPERADMIN and MALL_ADMIN: every control.

  This is client-side only. The server accepts a write from any role until R2 (E-20, waiver 3; AC-31). Per-venue grants are not applied in the client; they are R2's (AC-31). Verify: widget test (each role's screens with the registry's marker); no API test, because the server does not check roles until R2.
- **AC-37 (A10, the tenant in the admin page):** Choosing an account and, for an account holding two tenants, a tenant in FF-SK's switcher makes every FF-1 list, read and write use that tenant (the switcher's `X-Tenant-Id`). FF-1 adds no tenant control of its own. Verify: the manual case of AC-22; the API side is AC-22's API test.
- **AC-38 (G3, the decimal input form):** A decimal is accepted only as optional minus, digits, and optionally a point followed by digits (for example "12", "-4.5", "0.50"). A value typed as ".5" or "5." is refused on the client and on the server, with a message that names the field. The decimal field's hint shows the accepted form, "0.50". Nothing is ever rounded or corrected silently. Verify: widget test (".5" and "5." refused; the hint shown); API test (".5" and "5." refused with 400 on each record kind).

## 3. Edge cases

Each one gets a test in the plan, or a one-line reason why not.

**Offline or stale data**
- The admin page loses the API mid-list: the error state with Retry; already-loaded rows are not wiped by a failed "Load more" (S9's `loadMoreError`).
- The API is lost mid-save or mid-delete: the form keeps its values (AC-18), and the record is not shown as removed.
- A stale shopper package: not applicable. No publish exists until FF-3, and no venue draft reaches a shopper until it is published. FF-3's spec owns that edge.

**Empty and maximum data**
- A tenant with no venues, a venue with no buildings, a building with no levels, and a venue with no outdoor ground level: each list or section shows its empty state with a create action (for a VIEWER, without one; AC-36).
- A search with no match: the empty state, worded for a search.
- A venue with no level stores the zero-size boundary, and deleting its last level returns it to zero-size (AC-34; the degenerate-boundary test, G4).
- Exactly maximum lengths are accepted (Name 200, Code 40, ShortName 10, SpokenName 100, Level.Name 100). One more character is refused on the client and the server.
- Lengths are counted in characters, not bytes: "Ñ" and other non-ASCII names, for example "Parañaque Annex", are accepted up to the column's length (PostgreSQL `VARCHAR(n)` counts characters).
- Decimal limits:
  - `DECIMAL(9,3)` (`ElevationM`, `WidthM`, `DepthM`) takes at most 999999.999 and three decimal places; `ElevationM` takes −999999.999 too;
  - `WidthM` and `DepthM`: 0.001 is accepted, and 0 and any negative value refused (B6);
  - `DECIMAL(6,2)` `MapUpDeg`: 359.99 is accepted and 360.00 refused;
  - `DECIMAL(5,2)` `GridCellM`: 0.25 and 2.00 are accepted, and 0.24 and 2.01 refused;
  - `DECIMAL(5,2)` `CeilingHeightM`: 0.01 and 999.99 are accepted, and 0 and any negative value refused (B6);
  - one decimal place too many is refused, never rounded silently.
- `Ordinal` at the `INT` limits (−2147483648 and 2147483647) is accepted; beyond them it is refused as not an integer.
- A requested `pageSize` of 0, a negative one, a non-number or one above 200 gets the default or the cap (`parsePaging`). "Load more" on the last page loads nothing more and hides the footer.
- A tenant whose list passes one page: the scale case (§5).

**Tenant boundary**
- AC-22's cross-tenant read, update, delete and create-under.
- Another tenant's building type (AC-6).
- `X-Tenant-Id` naming a tenant the acting user does not hold: 403 (FF-0 §2). FF-SK's switcher offers only the tenants the chosen account holds (A10), so this is an API test only.
- The same venue Code in two tenants is allowed (AC-4).

**Each role**
- The client hides writes per role (AC-36), tested with each of the four roles' registry entries.
- The server's role behaviour is AC-31, waived to R1 and R2: until then a VIEWER's write sent directly (for example by curl with `X-Dev-Act-As`) succeeds. Reason not tested now: no role check exists before R2 (E-20, waiver 3); the ledger row records it.

**Permission denied**
- A 403 from the API (today only the stub's header checks) is shown through `formatApiError` in the list's error state or on the form, never as raw text (AC-18). The role-based 403s are AC-31 (R2).

**Concurrent edits**
- Two admins edit the same venue, building or level: the second save with the older `UpdatedAt` gets 409 (AC-25).
- A level is created, edited or deleted while a venue form is open: the venue form's save still succeeds, because the boundary refresh does not touch the venue's `UpdatedAt` (AC-34).
- Two admins create venues with the same Code at the same time: one succeeds, and the other gets AC-4's 409 (the unique index decides; no pre-check race).
- Two level writes in one venue that would give the same ordinal in one building, or a second outdoor ground level: the service serialises level writes per venue, so the second gets 409 (AC-12, AC-35). The plan states how (G4: the venue row is locked `FOR NO KEY UPDATE`, so other inserts under the venue are not blocked). These are tested in sequence, never by firing concurrent requests through one savepoint connection (G4).
- A building or level is edited after another admin deleted it: the save gets 404, and the form keeps the values (AC-18).
- A building is deleted while another admin adds a level under it: one of the two wins; a delete that loses gets AC-24's 409, and a level create that loses gets 404. The plan's shared venue lock decides (G4: the two deletes take the same lock).

**Publish in progress**
- Not applicable in FF-1: there is no publish, and no `VenueVersion` row is written. FF-3's spec must decide whether an edit during a publish is held, refused or read from a snapshot. Recorded here so it is not lost.
- FF-1 never writes or updates `VenueVersion` (the frozen-row trap). Verify: review.

**Invalid input**
- Each AC-17 case.
- A decimal typed as ".5" or "5." (AC-38, G3), with a comma ("1,5"), with spaces, in exponent form ("1e3"), or sent as a JSON number: refused with the field named, never parsed as something else.
- A malformed JSON body: 400 "Malformed JSON body" (the existing `errors.js`).
- Unknown extra fields in a body, a `boundary` among them, are ignored, never written. Whether to refuse them instead waits for R5's zod, because FF-1 has no schema validator (E-20).
- A building with no type chosen: refused on the client as required, and with 400 on the server (`BuildingTypeId` is NOT NULL).
- An outdoor level sent with a non-zero ordinal: 400 (AC-12).
- An id in the URL that is not a positive integer, 0 included: 404, never a 500. The id is refused before any query (G4).
- Whitespace-only required text: refused. Optional text that is blank stores NULL (`SpokenName`; `NULL = Name`).
- Venue Codes that differ only in case ("aurora", "AURORA"): both accepted (AC-4, B11).

**Lookups**
- The building type is deactivated while a building's form is open: the save keeps the type (AC-9).
- A type is deactivated and a new building is created, or another building is changed to it: the picker does not offer it, and the server refuses it (AC-10).
- A tenant's own type and a platform type with the same label: both are offered. Which code each has is not shown; the picker shows the label only, as in FF-0.
- No active building types at all, so the picker is empty: the picker's empty state. The building cannot be saved, because its type is required.

**Integrity**
- Pairing a level with a building of another venue (AC-13).
- An indoor level without a building, or an outdoor level with one (AC-13).
- Duplicate ordinals in one building (AC-35), and a second outdoor ground level per venue (AC-12).
- Deleting a building that has levels, or a level that is referenced (AC-24).
- An inactive venue: listed, marked, editable, and its buildings and levels editable (AC-24).

## 5. Scale targets

- **Venue size: up to about 100,000 m² per site** (PRD §7). A level's `WidthM` × `DepthM` for such a site is well within `DECIMAL(9,3)`. No area cap is applied to a level: that is a scale target, not a rule (r1 Q6, ruled with B6).
- **Tenants: up to about 5 mall-operator tenants at the pilot** (PRD §7).
- **Peak concurrent admins and requests per hour: measured at the pilot** (PRD §7, L109; Blueprint OQ1). No target is set here.
- **Page size:** default 25, capped at 200 (`functions/src/utils/pagination.js`, `DEFAULT_PAGE_SIZE` and `MAX_PAGE_SIZE`; standard §3.11, §3.19).
- **Venues per tenant, buildings per venue and levels per building:** no count target (B12). Server paging serves any count; no count limit is enforced or tested beyond paging.
- **Seed shape for reference, not a target:** Demo Malls holds four venues; the Aurora seed has five levels with two basements and a car park (FEATURE_PIPELINE P0-02, L102).
