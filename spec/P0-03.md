## 1. What this delivers

A mall admin presses **Publish** on a venue in the admin page. The server checks the venue and does one of two things:
- It refuses, and lists every problem in plain words, each one shown on a flat map of its level.
- It generates the walkway graph, costs the connectors, joins the walk-through stores and marks passages, and writes one immutable package file with its SHA-256 as a new `VenueVersion`.

Shoppers' apps download that package later (P0-04). Nothing here runs on a phone.

## 3. Acceptance criteria

Terms used below:
- **Place:** an active `Occupant` (through its unit's doors), an `Amenity`, a `TransitPoint` or an `Anchor`. All four must be reachable (ruled D5).
- **Element:** any row of `Unit`, `Opening`, `FloorObject`, `Amenity`, `TransitPoint`, `Anchor`, `NavConnector`, `NavConnectorStop`, `Beacon` or `NavCorrection` of the venue.
- **Wall (ruled D4):** each edge of a non-walkable unit's outline is a wall, except where one of that unit's `Opening`s sits on it. The outline of a floor object with `BlocksWalk` also counts as a wall for the crossing check.
- **Problem:** a reason publish refuses. **Warning:** a reason it reports without refusing.

### 3.1 Running a publish

- AC-1: A publish request for a venue of the request's tenant runs these steps in order: validation, graph generation, connector costing, walk-through stores and passages, then the package. It ends one of two ways: **published** (a new `VenueVersion` with `Status = 'PUBLISHED'`) or **refused** (the full problem list). The request waits until the publish ends, with no background job (ruled D3). Verify: integration (API against the seeded database).
- AC-2: A refused publish leaves no `VenueVersion` row of any status and no package file (ruled D3). Its problems exist only in the response. The response lists every problem found in that run, none dropped (DC-1). Each problem carries a kind, a plain-language message, its level, and the element it concerns and/or a location in level metres. `FAILED` is used only for build errors after validation (AC-9, AC-10). Verify: API.
- AC-3: A published version's row has:
  - `VersionNo` = the venue's highest existing `VersionNo` + 1 (DC-8);
  - `PackageFileId` pointing at a `StoredFile` row with `Purpose = 'PACKAGE'` and the request's tenant;
  - `PackageSha256` as 64 lowercase hex characters;
  - `PackageFormatVersion` = the format constant (1 for the first format);
  - `NodeCount` and `EdgeCount` equal to the package's graph;
  - `PublishedAt` in UTC;
  - `PublishedBy` and `CreatedBy` = the stub's actor user id.

  Verify: integration.
- AC-4: `PackageSha256` equals `StoredFile.Sha256`. Both equal the SHA-256 of exactly the bytes the storage holds, and the test recomputes it on its own from those bytes. Nothing is hashed before or after any other step: not before a compression step, and not as re-encoded for HTTP. This agrees with P0-04 AC-6, where the served bytes' SHA-256 equals `PackageSha256`. Only whether the stored bytes are gzipped is [S2: provisional] (§2). Verify: integration.
- AC-5: Publishing never updates or deletes a `PUBLISHED` row. A correction is always a new version (invariant 3; the frozen-row trap). A test publishes the same venue twice and checks that version 1's row is unchanged. A direct `UPDATE` of it still raises `TR_VenueVersion_Frozen`'s error. Verify: integration.
- AC-6: A new publish leaves every earlier version's package file byte-identical and readable (PRD §6.3: a shopper keeps the old version until the new one is verified). Verify: integration (hash before and after).
- AC-7: While a publish of a venue is `BUILDING`, a second publish of the same venue is refused with HTTP 409 and the message "A publish is already running for this venue". The refused request creates no row and no file. Publishes of two different venues do not block each other. Verify: API (two concurrent requests).
- AC-8: The package reflects the venue's draft at one moment (DC-2). An edit committed while a build is running is not in that version; it is in the next one. Verify: integration (an edit injected mid-build through a test hook).
- AC-9: A failure after validation passes (for example, the file cannot be written) has these outcomes:
  - the row ends `FAILED`;
  - no partial package file is left;
  - the response is a 500 in the standard error shape with the request id and no raw exception text;
  - the venue's latest `PUBLISHED` version is unchanged.

  Verify: integration (fault injected).
- AC-10: A process that dies can leave a `BUILDING` row behind. Once that row is older than a stale limit, the next publish of the venue sets it to `FAILED` and then goes ahead, so recovery is automatic (ruled D3). The limit is a setting (C8). Its value is provisional until it is sized from the time a full Aurora publish takes, which is measured in stage B. Verify: integration.

### 3.2 Validation: refusals (PRD §6.3; L92; L108)

- AC-11: **Unreviewed drafts (L108).** Publish is refused while any `Unit`, `Opening`, `FloorObject` or `NavConnector` of the venue has `NeedsReview = TRUE`. Each one is listed with its kind, name (if any) and level, and shown on the map. Verify: integration (the MEZZ seed's `NeedsReview` doors are each listed).
- AC-12: **No walkway through a wall (L92; walls ruled D4).** Publish is refused if any generated walkway, or any `ADD_PATH` correction, crosses a wall as defined in §3: a non-walkable unit's outline away from its openings, or the outline of a `BlocksWalk` floor object. The crossing point is shown on the map. Verify: unit (geometry fixtures, including a walkway through a blocking floor object and one through a door gap, which is allowed) and integration.
- AC-13: **Reachability (PRD §6.3 "every store reachable"; ruled D5).** Publish is refused if a place cannot be reached. Each unreachable place is named and shown at its door. A place counts as reachable only if all of these hold:
  - every active occupant is reached through at least one of its doors; amenities, transit points and anchors are reached at their own position;
  - it can be reached from at least one venue entrance, and a way leads back from it to one;
  - only everyday connectors are counted (evacuation-only connectors are not);
  - walk-through stores count as passages (AC-39). A place that can only be reached through a store the mall has not marked `PassThrough` is unreachable (L92, Risks);
  - publish runs no step-free check (PRD §6.7 has the app say "no step-free route");
  - a nested section (`ParentUnitId`) with no reachable door of its own is reached through its parent's doors.

  Verify: unit and integration.
- AC-14: **No orphan paths.** Publish is refused if any part of the walkway graph is not joined to the part that holds the venue's entrances. This includes an `ADD_PATH` whose ends do not join the graph (DC-6). Each orphan part is shown. Verify: unit.
- AC-15: **Connectors paired.** Publish is refused, with the faulty end shown, if any of these hold:
  - (a) a stairs, escalator or ramp row lacks `ToLevelId`, `ToX` or `ToY`, or has both ends on the same level;
  - (b) a lift has fewer than two `NavConnectorStop` rows on different levels;
  - (c) any end or stop does not lie on the walkable area of its level and so cannot join the graph;
  - (d) a stairs, escalator or ramp row has no `RiseM` (the rise trap, Blueprint Part 1).

  A lift needs no `RiseM` (ruled D7). Its rise between two stops is the difference of their levels' `ElevationM` (AC-33). Verify: unit and integration.
- AC-16: **Inside the boundary (invariant 10).** Publish is refused if any element is outside `Venue.BoundaryGeoJson`, and each such element is shown. The elements are: units, openings, floor objects, amenities, transit points, anchors, connector ends and stops, beacons and corrections. A point or shape on the boundary line counts as inside (DC-12; L30 puts transit points "at its edge"). Verify: unit.
- AC-17: **No beacon identity collision (invariant 9).** Among active beacons:
  - no two share (`ProximityUuid`, `Major`, `Minor`) anywhere on the platform;
  - every beacon's `ProximityUuid` is its tenant's `BeaconProximityUuid`.

  If either fails, publish is refused and both beacons are shown. The database already enforces both (`UQ_Beacon_Identity`, `FK_Beacon_Namespace`), so this check is defence in depth and is tested on in-memory data. Publish does not check D9's "identifier range per floor" (ruled D9: not yet). That rule is defined with P0-12 and P0-13. Verify: unit.
- AC-18: **Unreadable shapes (DC-4).** An element whose geometry is not a readable polygon, line or point is listed as "This shape can't be read" with the element named, and publish is refused. Examples: an unclosed ring, fewer than three distinct points, a self-intersecting outline, or the wrong GeoJSON type. Verify: unit.
- AC-19: **Tenant consistency (Blueprint DC8, re-checked at publish; DC-10).** An element that references a lookup row belonging to another tenant refuses the publish (for example, a `NavConnector` whose `ConnectorType` row is another tenant's). Verify: integration.
- AC-20: **Nothing to publish (DC-5).** A venue with no walkable area on any level is refused with "Nothing to publish: no walkways". Verify: unit.
- AC-21: Every check runs on every publish. A venue with one fault of each kind gets one response listing all of them (DC-1). Verify: unit.

### 3.3 Validation: warnings (never block)

- AC-22: **No beacons on this level (ruled D8).** Each level with no active beacon gets the warning "No beacons on this level", reported with the result. It never refuses a publish. Every Demo Malls venue therefore publishes with this warning on every level (L119: no beacons). PRD §6.3's coverage-gap and near-collinear warnings are **not** built in FF-3. They are added, as provisional settings (L117), once Spike 1's figures exist. This is recorded as a G4 difference. Verify: unit and integration.
- AC-23: **Unmeasured door width (L88, Risks: "An unmeasured door (NULL) needs a publish warning").** Each `Opening` with `ClearWidthM` NULL is a warning, not a refusal. Verify: unit.

### 3.4 Graph generation (L32; Blueprint §3.4 DC2)

- AC-24: The walkway graph is generated per level from the walkable area. The walkable area is the walkable units (`IsWalkable`), minus non-walkable units, minus floor objects with `BlocksWalk`, minus `BLOCK_AREA` corrections. Every node and every walk edge lies inside it. Verify: unit (property test over fixtures).
- AC-25: Every door (`Opening`) of a unit that holds a place is joined to the graph by an edge through that door's gap. Every venue entrance (`IsVenueEntrance`) is a node. Verify: unit.
- AC-26: Every connector end and every lift stop is a node joined to its level's walkable area. Verify: unit.
- AC-27: Corrections are applied as DC-6 states: `ADD_PATH`, `REMOVE_PATH` and `BLOCK_AREA`. A walkway added by `ADD_PATH` is subject to the wall check (AC-12) and the orphan check (AC-14). Verify: unit.
- AC-28: **Same-height joins (ruled D6).** Walkable areas on different `Level` rows with equal `ElevationM` are joined automatically wherever they touch or overlap in the venue's site frame. No connector is needed. Examples: a building's ground floor and the venue's outdoor ground, or a footbridge on one building's level. Verify: unit (fixture) and integration (Meridian Twin Malls and Aurora from the seed).
- AC-29: A walk edge costs its length in metres, measured in the level's planar metres (invariant 2). Verify: unit.
- AC-30: **Clearance (L88; Blueprint OQ7).** Every walk edge carries a clearance in metres, worked out from the walkable area's geometry. An edge through a door carries the smaller of that and the door's `ClearWidthM`. Where `ClearWidthM` is NULL, the geometry figure is used and AC-23's warning is raised. Verify: unit.
- AC-31: **Deterministic (DC-3).** The same draft and settings always produce the same nodes and edges, in the same order. Verify: unit (generate twice and compare).
- AC-32: **Graph density [S2: provisional].** The spacing between generated nodes is a setting, not a literal (C8). On the synthetic 100,000 m² venue (AC-69), the graph stays within about 20,000 nodes (PRD §7). A graph above that gets AC-75's warning and is never refused (ruled D14). Verify: integration.

### 3.5 Connector costing (L86, L91; invariant 15)

- AC-33: Taking a connector between two levels costs `CostBaseM + CostPerRiseM × rise`, from its `ConnectorType`. The type row is the tenant's own where one exists, else the platform default (the global-lookup trap). For stairs, escalators and ramps, the rise is `RiseM`. For a lift, the rise between two stops is the difference of their levels' `ElevationM`, and every pair of stops gets an edge (ruled D7). A tenant's tuned values are used. Example: with the seeded defaults, an escalator with a 4.5 m rise costs 14 + 1 × 4.5 = 18.5 m. Verify: unit and integration.
- AC-34: A connector with `IsBidirectional = FALSE` gets a From → To edge only. With `TRUE` it gets both directions (L86). Verify: unit.
- AC-35: Connectors with `IsEvacuationOnly = TRUE` are in the graph and flagged evacuation-only (L87). Routing decides when to use them (P0-06, P3-02). Verify: unit.
- AC-36: **Inactive lookup value (FEATURE_PIPELINE §5 item 15).** If a `ConnectorType`, `AmenityType`, `OccupantCategory` or `StoreStatus` row that a venue still references is deactivated, the next publish still uses and carries that row's values. Verify: integration (in `npm run verify`).

### 3.6 Walk-through stores and passages (L92; Blueprint §4.1)

- AC-37: For each unit with `PassThrough = TRUE`:
  - each of its doors joins a point just inside the store;
  - those points are joined to each other across the store's floor.

  Each such edge carries:
  - the store's unit id;
  - its real length;
  - a cost of length × the store-crossing factor. The factor is a tenant setting with default 1.25 (L92 ruling 6). The key is named in the plan and listed in `functions/src/config/settings.js` before use. It is a `routing.*` key, so it travels in the package (AC-72).

  Verify: unit.
- AC-38: A store not marked `PassThrough` gets no edges across its floor. Its doors join only to its own place. Verify: unit.
- AC-39: **Passages (ruled D10).** Publish finds each place that cannot be reached without crossing a walk-through store, and marks the store(s) concerned as passages for that place in the package. The admin sets nothing extra (L92 ruling 3). When more than one walk-through store would do, every one of them becomes a passage for that place, and the router picks the shorter way. Verify: unit and integration.
- AC-40: A place that can only be reached through an unmarked store is unreachable and refuses the publish (AC-13). Verify: unit.

### 3.7 The package (D6; invariant 8) [S2: provisional throughout, except AC-4's hash rule]

**The allow-list (ruled D11, with A3 and A9).** The package holds these and nothing else:
- venue (code, name, boundary, georeference, `MapUpDeg`, `EvacEscalatorsAllowed`);
- buildings (name, type label, footprint, `MapUpDeg`);
- levels (ordinal, names, `SpokenName`, outdoor flag, elevation, size);
- units (category, name, outline, walkable, walk-through, parent);
- openings (outline, entrance flag, clear width);
- floor objects (outline, height, blocks walk);
- active occupants (name, category, keywords, `SpokenName`, status and `IsRoutable`);
- amenities with type, synonyms and accessible flag;
- transit points and anchors;
- connectors: type, **`Name`** (A9), cost model, step-free flag, ends or stops, one-way, evacuation-only, and `SpokenName`;
- active beacons (UUID, Major, Minor, level, x, y, mount height, measured power);
- the graph, the passages, the FTS5 index, the R*Tree indexes (walk edges, unit outlines and **wall segments**, A9) and the metadata;
- every `routing.*` setting, as resolved for the venue's tenant at publish (A3).

The package leaves out: inactive occupants and beacons; logos (none are uploaded yet); every setting that is not `routing.*` (A3 sends those, `package.refreshCheckS` now, through the public mall list, P0-04); and every column AC-46 names.

- AC-41: Each published version is one SQLite file:
  - written with `better-sqlite3` (E-03) using raw parameterized SQL only;
  - opens read-only;
  - passes `PRAGMA integrity_check`;
  - has working FTS5 and R*Tree tables.

  Verify: integration (the test opens it read-only).
- AC-42: The package holds the CSR graph: nodes with their level and x, y; directed edges with target, cost, real length, clearance, kind (walk, connector or store crossing), connector id or store unit id, and the evacuation flag. A test decodes it and compares it with the generator's output. The layout and number types are set by stage B after FF-S2 reports (ruled D1). Verify: integration.
- AC-43: The package holds an FTS5 index over occupant names and `SearchKeywords`, occupant category labels, amenity type labels and `SearchSynonyms`, transit point names, anchor names and nested sections (P0-05; Blueprint §4.7). Example: in Aurora, "comfort room" and "cr" each find a restroom. Verify: integration.
- AC-44: The package holds R*Tree indexes per level over the walk edges (the RG3 origin snap) and over the unit outlines (hit-testing). The wall-segment index is AC-71. Verify: integration.
- AC-45: The package carries each building's `MapUpDeg` (the venue's where the building has none), the venue's `MapUpDeg`, and every `SpokenName` on `Level`, `Occupant` and `NavConnector` (L111, L112; FEATURE_PIPELINE P0-03). Verify: integration.
- AC-46: **Sealed package (invariant 8).** The package contains only the allow-listed tables and columns (above, ruled D11), and never any of these:
  - secrets;
  - audit columns;
  - `NeedsReview` or `DraftConfidence`;
  - beacon `InstalledOn`, `BatteryServicedOn` or `BeaconPlanItemId`;
  - sentinel data;
  - anything about users;
  - any setting that is not `routing.*` (A3).

  A test compares the package's schema with the allow-list in code. Verify: unit.
- AC-47: The package carries each occupant's store status as of publish, with its `IsRoutable` (PRD §6.5; L83). Verify: integration.
- AC-48: The package carries a metadata table: format version, venue code, version number and publish time (DC-7). Verify: integration.
- AC-49: The package holds rows of the published venue only. No unit, occupant, beacon, connector or setting of another venue or another tenant appears in it (invariant 13). The test publishes a Demo Malls venue while both tenants are seeded, then searches the package for the other venues' names and beacon identities. Verify: integration.

### 3.8 Storage under E-20 (ruled D2)

- AC-50: The package file is written under a local folder named by an environment value (documented in `.env.example`; the sync table's setting row).
  - The folder is git-ignored. `git check-ignore` passes for a written file, because the penthouse package holds internal-only data (L48, L123).
  - No Cloud Storage client is created or called.
  - The `StoredFile` row records `Purpose = 'PACKAGE'`, the tenant, `MimeType`, `SizeBytes`, `Sha256` and `StoragePath`.
  - `StoragePath` is a storage key shaped like the future Cloud Storage object path. It holds the tenant id and the venue id, and is never an absolute or relative disk path (§2).

  Verify: integration.
- AC-51: The publish engine writes and reads packages only through one storage interface, so the deploy call can swap the local folder for Cloud Storage without editing the engine (DC-13). Verify: review, plus a unit test of the local implementation.

### 3.9 Tenant, roles and input

- AC-52: Every query binds the tenant from `req.tenantCompanyID`, and the venue from the request, checked against that tenant (rule 2; invariant 13). Publishing a venue id that belongs to another tenant answers 404 and creates nothing. The `tenant-predicate` lint passes. Verify: API.
- AC-53: Under the stub, an `X-Tenant-Id` naming a tenant the stub's user does not hold answers 403 (FF-0's behaviour). One publish case confirms the route sits behind the stub. Verify: API.
- AC-54: **Deferred to R2, not tested in FF-3.** A `VENUE_EDITOR` or `VIEWER` gets 403 on publish; a `MALL_ADMIN` of the venue's tenant (with a venue grant) or a `SUPERADMIN` may publish. Publishing is Create on `venue-versions` (Blueprint §2.4). Recorded as a retrofit-ledger row. Verify: R12 e2e.
- AC-55: A publish writes no `AuditLog` row until R3 (E-20). `CreatedBy` and `PublishedBy` hold the stub's user id. Verify: integration.
- AC-56: A venue id that is not a positive integer gets a 400 in the standard error shape and never reaches SQL as text (rule 3). Examples: `abc`, `-1`, `1.5`, or a number larger than an `INT`. Verify: API.

### 3.10 The admin publish screen (flutter-coder)

- AC-57: From FF-1's venue screen, a "Publish" entry opens the publish screen. The screen shows the venue's latest published version (number, date and time, package size, node and edge counts, the first 12 characters of its SHA-256), or "Not published yet". Verify: widget and screenshot.
- AC-58: Pressing Publish disables the button and shows that publishing is under way. It ends in one of two states:
  - **success:** the new version's summary and its warnings;
  - **refused:** "Not published" with the problem list.

  Verify: widget.
- AC-59: The problem list and the warning list are grouped by kind, and each row has a plain message and its level. Tapping a row shows that level on the map with the problem highlighted. The lists use S9's list scaffold, with all four states (loading, empty, error, data). Verify: widget.
- AC-60: **The map (ruled D12).** A read-only flat map of one level at a time, with level chips, drawn with `flutter_map` and `CrsSimple`. It draws units, doors, connectors, beacons and the problem and warning markers, from the drawing route (AC-73). All colours come from `gabay_tokens.dart` through `colorScheme` (rule 6). EXCEPTIONS E-04's wording widens from "the admin's flat editor only" to "the admin's flat maps", with the product owner's sign-off (D12). The `flutter_map` pin comes from Blueprint Part 1 and is rechecked on pub.dev at install (RECALLED until then). Verify: widget, plus screenshots in light and dark, phone and tablet widths.
- AC-61: **Walkways (ruled D12).** After a successful publish, the map also draws that version's generated walkways on the shown level. They are read through the drawing route with `versionNo` (AC-73). [S2: provisional for how the walkways are read from the package] Verify: widget.
- AC-62: If the screen opens while a publish of the venue is `BUILDING`, or a press gets the 409, the screen shows "A publish is already running for this venue" and keeps the button disabled until the user refreshes and that publish has ended. Verify: widget.
- AC-63: Network and server errors go through `formatApiError` (no raw exception text) with a retry. Examples: offline, the API down, a 500. Verify: widget.
- AC-64: Returning from the publish screen refreshes the venue screen's version information (`didPopNext`). Verify: widget.

### 3.11 The seeds and scale

## 4. Edge cases

Each edge case below is covered by the criterion named, or has a one-line reason.

**Offline or stale package**
- EC-1: A shopper's phone holds version N while N+1 is published. N's file and row are untouched (AC-6). How the app swaps is P0-04's job.
- EC-2: The admin page is offline or the API is down when Publish is pressed. The error state appears with a retry (AC-63) and nothing is created on the server.
- EC-3: A publish runs on settings and lookup costs as they are at that moment. Changing a cost or a `routing.*` value afterwards changes nothing until the next publish (AC-8, AC-33, AC-72). The old package keeps its values.

**Empty and maximum data**
- EC-4: A venue with no levels, or no walkable area, is refused (AC-20).
- EC-5: A venue with walkways but no places publishes, because nothing fails reachability. It still gets the "No beacons on this level" warnings if it has no beacons (AC-22).
- EC-6: A level with nothing on it adds no nodes and raises no problem. Its only possible warning is "No beacons on this level" (AC-22). The warning kinds are the stated ones (AC-22, AC-23, AC-75) and no others are invented.
- EC-7: The largest venue: about 100,000 m² and about 20,000 nodes (AC-69). Above that, a warning only (AC-75). About 400 places on five levels, as Aurora has (FEATURE_PIPELINE P0-02, L102), is covered by AC-66.
- EC-8: Very long text (`SearchKeywords` at 400 characters, names at 200) and non-ASCII names (ñ, Tagalog words) are stored and found by FTS5 (AC-43, with fixtures).
- EC-9: Hundreds of problems at once, for example a whole floor of unreviewed draft elements: all are returned (AC-2), and the list pages through the scaffold (AC-59).
- EC-37: A large level on the drawing route (Aurora has 2,320 units across the venue). The route answers for one level at a time (AC-73), so no response holds the whole venue.

**Tenant boundary**
- EC-10: A venue id from the other seeded tenant without the header gets 404 (AC-52). With a header naming a tenant the user lacks, it gets 403 (AC-53). The drawing route behaves the same (AC-74).
- EC-11: An element that points at another tenant's lookup row refuses the publish (AC-19).
- EC-12: Two tenants may each have a venue with the same `Code`. Packages and storage keys never collide, because the key holds the tenant id and the venue id (AC-50, D2) and the version row is per tenant (`UQ_VenueVersion`). No other venue's rows leak into a package (AC-49).
- EC-38: The dev command publishes another tenant's venues by design (AC-68, D13). It runs only where the stub runs, and it still binds each venue's own tenant in every query (rule 2).

**Each role, and permission denied**
- EC-13: MALL_ADMIN publishes (the stub acts as this role by default, L154). VENUE_EDITOR and VIEWER are refused with 403 from R2 (AC-54). Until then, the switcher can act as them and the server does not refuse. SUPERADMIN acting as a tenant is R1/R2. None of these is tested in FF-3 because of the E-20 waiver; each is on the ledger.
- EC-14: A missing venue grant (`UserVenueGrant`) is R1's tenant-and-venue check, which the stub does not do. It is on the ledger.

**Concurrent edits and publish-in-progress**
- EC-15: Two Publish presses on one venue: one runs, the other gets 409 (AC-7). The same applies to the dev command against a venue whose publish is running.
- EC-16: Two venues publishing at once: both proceed (AC-7). FF-3 runs on one machine with `maxInstances = 1` in mind (Blueprint Part 1).
- EC-17: The draft is edited while a build runs. The edit lands in the next version (AC-8).
- EC-18: The server dies mid-build and a `BUILDING` row is left behind. Once it passes the stale limit, the next publish sets it to `FAILED` and goes ahead (AC-10, D3).
- EC-19: The admin reloads the screen while a publish is running. The screen reads the `BUILDING` state (AC-62).
- EC-39: The draft is edited after version n, then the map asks for version n's walkways. The outlines are the draft's and the walkways are version n's (AC-73). They may disagree until the next publish. This is expected and is not a fault.

**Invalid input and bad data**
- EC-20: A non-integer, negative or oversized venue id gets 400 (AC-56). A venue id that does not exist gets 404. On the drawing route, the same applies to `levelId` and `versionNo` (AC-74).
- EC-21: An unreadable shape refuses the publish (AC-18).
- EC-22: Stairs, an escalator or a ramp without `RiseM` refuses the publish (AC-15d). A lift without `RiseM` publishes, with its rise taken from its stops' `ElevationM` (AC-15, AC-33, D7).
- EC-23: A connector end off the walkable area, a lift with one stop, or a two-ended connector with both ends on one level refuses the publish (AC-15).
- EC-24: An `ADD_PATH` through a wall or a blocking floor object refuses the publish (AC-12). An `ADD_PATH` whose ends join nothing refuses it as an orphan (AC-14). A `REMOVE_PATH` that cuts a place off refuses it as unreachable (AC-13).
- EC-25: A one-way escalator is the only way up to a floor, with no way back down. The places up there have no way back to an entrance, so they are unreachable and the publish is refused (AC-13, D5).
- EC-26: Evacuation-only stairs are the only way to a place. Evacuation-only connectors do not count, so that place is unreachable and the publish is refused (AC-13, D5).
- EC-27: A place that can be reached only through a marked walk-through store becomes a passage (AC-39). If either of two such stores would do, both become passages for it (AC-39, D10). If the only way is through an unmarked store, the place is unreachable (AC-40).
- EC-28: A door with no measured width raises a warning (AC-23). Its edge's clearance comes from the geometry (AC-30).
- EC-29: A nested section (`ParentUnitId`) with no reachable door of its own is reached through its parent's doors (AC-13, D5). If the parent itself is unreachable, so is the section.
- EC-30: Beacons:
  - a Demo Malls venue (no beacons) gets "No beacons on this level" warnings only (AC-22);
  - an inactive beacon is left out of the package and the checks (allow-list, D11);
  - a duplicate identity cannot reach the database (`UQ_Beacon_Identity`), so it is tested on in-memory data (AC-17);
  - two levels sharing a Major are not checked (D9; AC-17).
- EC-31: A deactivated lookup row still referenced by the venue is published with its values (AC-36).
- EC-32: The disk is full or the folder cannot be written. The row ends `FAILED` with no partial file and the latest published version is unchanged (AC-9).
- EC-33: The same draft is published twice. The graph is identical (AC-31) and a new version is written. Refusing a publish when nothing changed is not stated anywhere, so it is not done.
- EC-34: Coordinates arrive as `DECIMAL(9,3)` strings from `pg`. Geometry is computed from parsed numbers, never by string comparison. Covered by unit fixtures that use database-shaped rows.
- EC-40: The seed is run again after a publish. It stops with the `setup-db` line and changes nothing (AC-76, A8).
- EC-41: The dev command is given a tenant code or a venue code that does not exist. It names the unknown code in one line, publishes nothing, and exits non-zero, so a mistyped code cannot pass silently (AC-68; Q17 (a)).
- EC-42: The drawing route is asked for `versionNo` before any publish, or for a `FAILED` version. Either way it answers 404 (AC-74). Without `versionNo`, it returns the draft outlines (AC-73).

**Rule-specific**
- EC-35: Money (rule 1): the package carries no money, and beacon prices are not in the allow-list (D11). Nothing to test beyond AC-46's seal.
- EC-36: Option lists (rule 5): problem kinds and warning kinds are closed sets owned by code. They go in the one constants file with an authority comment (FEATURE_PIPELINE §5 item 14), not in a lookup.

## 7. Design choices in this spec (accepted, D15, 2026-10-09)

The product owner accepted DC-1 to DC-13 as written (D15). Each one names an alternative that would also satisfy what is stated.

- **DC-1** Validation reports every problem in one run. *Alternative:* stop at the first problem (faster, but the admin fixes one fault per round).
- **DC-2** The build reads the draft in one consistent snapshot (one database transaction). *Alternative:* lock the venue against edits for the length of the build.
- **DC-3** Graph generation is deterministic. *Alternative:* test only the graph's properties (AC-24 to AC-30) and allow ordering to vary.
- **DC-4** An unreadable shape is a refusal. *Alternative:* skip the element with a warning (risk: a store silently missing from the package).
- **DC-5** A venue with no walkable area is refused. *Alternative:* publish an empty package.
- **DC-6** How corrections apply (L32 names the three kinds but not their exact effect):
  - `BLOCK_AREA` is subtracted from the walkable area before generation;
  - `ADD_PATH` adds edges along its line, and each end joins the nearest node within a snapping distance (a setting), else it is an orphan;
  - `REMOVE_PATH` removes every generated edge its geometry crosses.

  *Alternative:* `REMOVE_PATH` removes edges within a set distance of its line.
- **DC-7** The package carries its own metadata table. *Alternative:* metadata only in the database row and HTTP headers.
- **DC-8** Version numbers keep a `FAILED` row's number, so published numbers may have gaps. *Alternative:* reuse the number of a `FAILED` row.
- **DC-9** Every published package file is kept while E-20 is open. R13 recreates everything anyway. *Alternative:* keep the last N versions per venue.
- **DC-10** Publish re-checks "same tenant or platform" for lookup references. *Alternative:* trust the write-side checks (Blueprint DC8), which FF-1's routes must then guarantee.
- **DC-11** Every problem carries an element reference and/or a location, so the screen can show it on the map. *Alternative:* problems as text only (this would not meet "shown on the map", PRD §6.3).
- **DC-12** A point on the boundary line counts as inside (L30's "at its edge"). *Alternative:* a small tolerance setting.
- **DC-13** One storage interface with a local implementation now. *Alternative:* write files directly now and refactor at the deploy call.

## 9. Questions ruled (2026-10-09)

Genesis Perez, the product owner, answered every question in the FF-1 to FF-4 batch (`plan/FF-1-4-decisions.md`, APPROVED 2026-10-09). Each was answered as the batch sheet recommended. That matches r1's recommended option everywhere except Q9 (D8). The ruling is given first under each question, and the options that were offered are kept below it as the record.

**Q1 [spec-writer] Spike 2 has not run. What may FF-3 build before it reports?**
**Ruled 2026-10-09 (D1; option a):** everything except the package writer's format. Stage A starts now and stage B follows FF-S2's report. Applied in §2, AC-42 and §3.7.

What must wait for Spike 2:
- the container (SQLite as D6 ruled, against the FlatBuffers benchmark);
- the CSR graph layout and its number types (D6 cites `Float32List`/`Int32List`);
- whether the stored file is gzipped. Since r2, this no longer decides which bytes the SHA-256 covers: it covers exactly the stored bytes (AC-4);
- the FTS5 and R*Tree configuration;
- how much geometry detail the package carries;
- node spacing, and with it the node count.

Options offered:
- (a) The plan may start validation, graph generation, connector costing, passages, storage and the screen now. The package writer's format is fixed only after FF-S2 reports, and the plan cites the report. *Recommended; taken.*
- (b) Wait for FF-S2 before writing FF-3's plan.
- (c) Build everything now on D6 as ruled, and change it after Spike 2. A change after merge bumps `PackageFormatVersion`.

**Q2 [spec-writer] Is Spike 2 itself still scheduled before FF-3, as `plan/PH4-feature-first.md` §4 orders it?**
**Ruled 2026-10-09 (A5; option a):** yes. FF-S2 reports before FF-3's stage B (and before FF-4 starts). Applied in §2.
- (a) Yes: FF-S2 runs next, in parallel with FF-1 and FF-2 (capacity note). *Recommended; taken.*
- (b) No: FF-3 goes first, and the package format is revisited after FF-S2.

**Q3 [spec-writer] Where does the package go under E-20, what does `StoredFile.StoragePath` hold, and which slice closes the move to Cloud Storage?**
**Ruled 2026-10-09 (D2; option a):** a git-ignored local folder. `StoragePath` holds a key shaped like the future Cloud Storage path. The move to Cloud Storage gets a ledger row, closed at the deploy call. Applied in §2, AC-50, EC-12, §5 items 1 and the ledger.
- (a) A git-ignored local folder named by an `.env` value. `StoragePath` holds a storage key shaped like the future object path (for example `packages/<tenantId>/<venueId>/<versionNo>`), never an absolute disk path. One storage interface. The move to Cloud Storage gets a ledger row closed at the deploy call (OQ9), and the column comment is reworded to "the storage key". *Recommended; taken.*
- (b) The Firebase Storage emulator. It is local, with the same code path as Cloud Storage, but the intent says "no Cloud Storage" and it adds an emulator to `verify`.
- (c) Package bytes in PostgreSQL. This needs a new `BYTEA` column and a migration, and nothing goes to disk.

**Q4 [spec-writer] What does a publish leave behind, and how does it run?**
**Ruled 2026-10-09 (D3; options a, a, a):** a refused publish leaves no row, and `FAILED` is for build errors only. The request waits. The stuck-publish limit is a setting, sized from Aurora's publish time. Applied in AC-1, AC-2, AC-10 and EC-18.
- On a refusal:
  - (a) Validation runs before any row is created, so a refusal leaves no row and the problems live only in the response. `FAILED` is for build errors only, and no schema change is needed. *Recommended; taken.*
  - (b) Every attempt writes a row, `FAILED` with its problems. This needs a new JSONB column and a migration.
- Running:
  - (a) The request waits until the publish ends. This is the simplest on localhost and is revisited at OQ9. *Recommended; taken.*
  - (b) A background job, with the screen polling the `BUILDING` row.
- A stuck `BUILDING` row:
  - (a) A setting for the stale limit, with the value set from the time measured on Aurora. *Recommended; taken.*
  - (b) No automatic recovery: it is cleared by hand with a development command.

**Q5 [spec-writer] What is a "wall" for L92's check?** The schema has no wall table: walls are implied by unit outlines and their doors.
**Ruled 2026-10-09 (D4; option a):** non-walkable unit outlines are walls except at their doors, and walkways through blocking floor objects are refused too. Applied in §3 (terms), AC-12 and AC-71.
- (a) Every edge of a non-walkable unit's outline is a wall, except where one of that unit's `Opening`s sits on it. Blocking floor objects (`BlocksWalk`) are also refused if a walkway crosses them. *Recommended; taken.*
- (b) Only unit outlines are walls. Floor objects only shrink the walkable area and are not checked.

**Q6 [spec-writer] "Every store reachable": which places, from where, and how?**
**Ruled 2026-10-09 (D5; option a):** occupants, amenities, transit points and anchors, reached from an entrance and with a way back, over everyday connectors only, with no step-free check at publish. Applied in §3 (terms), AC-13, EC-25, EC-26 and EC-29.
- (a) Every active occupant (through at least one of its doors), amenity, transit point and anchor:
  - reachable from at least one venue entrance, and able to get back to one;
  - over everyday connectors only (evacuation-only connectors not counted);
  - with walk-through stores counted as passages;
