- `db/seeds/seed.js` with `lib/` (`db.js`, `geo.js`, `lookups.js`, `demo.js`, `spike.js`, `accounts.js`): one transaction; it first removes its own two tenants and six accounts, then writes the platform lookups and roles, the two tenants, the venues from JSON and the six accounts. ## 3. Behaviour without the owner's spike exports

`sources/spike-exports/` missing, empty, or holding no `.json` file (its README is not an export):
- the seed writes Demo Malls in full, MEZZ office, the penthouse when its internal source is present, and the six accounts;
- it prints one line saying no spike exports were found and where to put them (DESIGN CHOICE; the alternative, today's behaviour, is to print nothing);
- it commits and exits 0. Nothing waits on the exports, and adding them later needs only a re-run.

The same holds on a clean clone, in CI and in a coder working copy, where neither the internal source (unless `worktree:new` copied it) nor any export exists: Spike Venues then holds MEZZ office only, plus the penthouse where present. The exports are git-ignored (ruling C3) and `worktree:new` does not copy them (ruling C9).

## 5. Edge cases

Each has its behaviour and its test, or one line saying why there is no test.

- **No exports** (folder missing, empty, README only): §3, AC-7.
- **Penthouse source absent** (clean clone, CI, a working copy made without it): AC-5. `npm run worktree:new` already copies it from the main folder when the main folder has it.
- **Coder working copies have no exports** (they are git-ignored and `worktree:new` does not copy them): left as it is (ruling C9). The tests use invented fixtures (AC-8, AC-25), and the owner's exports live in the main folder. Test: none beyond AC-7, since nothing changes.
- **An export that cannot be read or does not fit:** AC-25, skipped with one line, the rest seeded, exit 0 (ruling C2). *Unverified (RECALLED):* that the spike's share-sheet export uses the same JSON shape as its bundled assets. This is checked against the first real export, before AC-8's fixture is final.
- **A new export added later:** Majors are given in file-name order from 3, so a file that sorts earlier moves the Majors of the files after it. This is accepted until FF-9 (ruling C1); the seed prints each venue's Major and the README says so. Test: integration (one file alone gets Major 3; with a file that sorts earlier added, that one gets 3 and the first gets 4).
- **An export with no rooms, no doors or no beacons:** it seeds the venue, its one building and its "Floor 1" level with whatever the file has, and no error. Test: integration (an invented fixture).
- **Maximum data:** Aurora (401 places) and Skyline Spire (16 levels) are the largest seeded venues. AC-2 covers them; the scale targets are §7.
- **Tenant boundary:** AC-12, AC-13, AC-16. Cross-tenant links are refused by the schema's composite foreign keys; AC-17's per-tenant counts would show a stray row. A version in another tenant does not stop the seed (AC-23).
- **Each role:** the rows are AC-10 and AC-11. What each role may do is not enforced until R2 (E-20; item 3 waived in P0-01 and later slices), so there is no role-behaviour test here. SUPERADMIN has no tenant row; the stub's behaviour for such a user is FF-0's and FF-SK's.
- **Permission denied:** a user asks for a tenant it does not hold: AC-12.
- **The stub's user is missing:** `npm run seed:db-only` deletes the six accounts and does not re-create them, so the dev stub cannot load malladmin@ until a full `npm run seed` (CLAUDE.md already warns). Unchanged by this spec (see Suggestions). Test: none, since the behaviour is unchanged and documented.
- **Stale ids after a re-seed:** every seeded row gets a new id, so an admin page left open shows ids that no longer exist. P0-01's not-found handling answers; nothing is added here. Test: P0-01's own not-found test.
- **Concurrent edits:** an admin edit to a seeded row while the seed runs either commits before the seed's delete (and is then removed) or waits and fails once the seed commits; P0-01 shows the error through `formatApiError`. Readers see the old seed or the new one, never a half, because the seed is one transaction. Test: AC-19 covers the all-or-nothing part. The interleaving itself is not tested, because its timing cannot be made deterministic without a test-only hook in the seed.
- **Two seeds at once:** verify's lock serialises its own runs. A run started by hand at the same time fails to start the Auth emulator on the shared ports (9099, 4400, 4500), and the database keeps one complete seed. Test: none, because port contention on a shared machine is not reproducible in CI; it is a manual smoke step.
- **Auth emulator account exists with another password** (`.env` changed): the existing error names the two fixes (clear `db/seeds/.emulator-data` or fix `.env`), and the run rolls back. Test: integration.
- **`.env` missing or a `SEED_PW_*` under 6 characters:** a missing `.env` means Node's `--env-file` fails before any database work; a short or missing key is AC-19. Test: integration for the key. A missing file is Node's own behaviour, so it gets no test.
- **verify wipes hand-made data:** verify's `schema-run` checks re-apply `db/schema.sql`, which drops every table, in the database verify uses. Hand-made rows there, published versions included, never survive a verify run, so verify's own `seed` check never meets AC-23's stop. This happens before P0-02 runs and is accepted by E-20 rule 3 (throwaway data). Test: none, since P0-02 does not change it.
- **Re-seed after a publish** (a test tenant holds a version, from FF-3 on): AC-23, the seed stops with the `setup-db` and `publish:dev` line.
- **Publish in progress during a seed run:** a publish that writes its version after the seed's AC-23 check makes the seed's venue delete fail on the version's reference (or wait for it), so the seed rolls back whole (AC-19's all-or-nothing) and the next run meets AC-23. Test: none for the interleaving, for the same reason as concurrent edits.
- **Offline or stale package:** the seed writes no package. After `setup-db` and `publish:dev`, a phone holding a package from before is P0-04's delivery case (decision sheet E6), not this spec's. Test: none here.
- **A Demo Malls venue and mall detection:** with no georeference (AC-24) a Demo Malls venue is never detected by location; the shopper picks it. Test: AC-24 for the seeded value; detection is P0-04's, with fixtures.
- **Invalid input in the committed sources** (demo JSON, `mezz.json`): these are fixed files under review. AC-1 to AC-4, AC-17 and AC-24 would fail on a damaged one.

## 7. Scale targets

- **Data size:** the seeds exist so that download, refresh and routing are "proven at mall scale" (FEATURE_PIPELINE P0-02, L102): Aurora is about 400 places (401, L120), and Skyline Spire has 16 levels (L119). Demo Malls' totals as recorded by L120 are AC-2.

- **Seed run time:** no target (ruling C5). Verify's existing 10-minute cap on the `seed` check (`tools/verify.js`, `TIMEOUT_MS.seed`) stands; it is a check timeout, not a target.
